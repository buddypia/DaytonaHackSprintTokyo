05Architecture

Every errand gets its own machine.

依頼ごとに専用の隔離マシンを1台。終わったら環境ごと破棄します。
◆  Daytona is the default runner. The same desktop image also runs on a GCP VM or local Docker, so the demo cannot be killed by a venue network.
◆  The model never receives a shell. It only receives text and returns one of 12 typed actions.
◆  Every action is one executeCommand inside the sandbox, logged with its output.
One process · one sandbox per errand · no shared state05 / 15

07The loop

The model chooses the move.
Code decides what is legal.

判断はモデル、禁止事項はコード。プロンプトで破れない場所にガードを置いています。
1 · No source, no input
DROP THE ACTION
Every fill or select must carry from, naming the record it came from. Unsourced values never reach the browser.
2 · Nothing left behind
SUBMIT BLOCKED
Each document field must be entered, or declared “not applicable” with a reason. The unresolved set must be empty before the final button exists.
3 · The last button is human
ASK FIRST
A submit action, or any click whose label looks like a final application, triggers a read-back and waits for an explicit “yes”.
4 · Bounded by construction
STOP GRACEFULLY
30 turns, 3 questions, 10 minutes of waiting. On any breach the sandbox is destroyed and the run is reported as failed — never as done.
guard log  ·  ✘ fill e9 “ひばり野銀行” — no from → action dropped  ·  ✘ submit e12 — unresolved: 生年月日 → rewind  ·  ⏸ click e12 — waiting for the human’s “yes”
Guardrails live in the harness, not in the prompt07 / 15

10Proof

Then it proves the filing — without asking a model.

送信後に、申請サイト自身の画面と入力記録を突き合わせます。合否はモデルではなく終了コードです。
FOUR ARTIFACTS IN THE SANDBOX
expected.json
What the agent typed, and from which source.
confirm-page.txt
The portal’s own view, saved just before submit.
done-page.txt
The receipt screen after submission.
site-received.json
What the portal actually stored, server-side.
TXT snapshots are produced by the browser step; the JSON is written by the orchestrator.
THE VERIFIER’S CHECKS — NO MODEL, NO NETWORK
✔  A confirmation page was captured before submit
✔  Every typed value appears on the portal’s confirmation page
✔  Every typed value has a recorded origin
✔  No document field was skipped without a stated reason
✔  The page after submit says “accepted / complete”
✔  The reported receipt number appears on that page
✔  Server-side values and receipt number match the client record
Why a second opinion matters: the agent could hallucinate a success screen. The verifier only reads files the portal produced, so a wrong answer fails loudly instead of quietly.
VERDICT
exit 0
any ✘ → exit 1 → run fails
A failure is visible, not hidden: the run ends as “sent, but inconsistent”, with the ✘ lines attached. It never reports “done”.
IMPLEMENTATION
One plain-JS file, no dependencies, no network. It prints a pass/fail line per check — a judge can read the verdict in the terminal during the demo.
sandbox/verify/verify.mjs
The success criterion is a file the portal wrote, not a sentence the model wrote10 / 15

Nosana
SPONSOR · INFERENCE
An OpenAI-compatible endpoint, so the same code runs on Nosana GPUs, on your own Vertex project, or on a laptop Ollama. The default for a privacy-sensitive deployment is Nosana.
Vision — reads the notice into a fixed JSON shape: type, deadline, three-line summary, person fields with source text + confidence.
Policy — decides the next browser action each turn, at temperature 0.
Latency hedge — if no answer in 6s, a second identical request is sent; the first reply wins.
Split roles — read a notice on Nosana, drive the browser on Vertex; one env var each.
AI_PROVIDER=nosana
OPERATOR_AI_PROVIDER=vertex
NOSANA_BASE_URL=https://…/v1
SANDBOX_PROVIDER
daytona · default gcp docker local · dev only
The same desktop image (Xvfb + xfce4 + x11vnc + noVNC) is reproducible outside Daytona, so a venue firewall can never turn the demo into a slide. The Daytona path is the production one: one sandbox per errand, deleted at the end.

14Against the rubric

Judged on four things. Here is the evidence.

4つの審査基準に対して、実装・実測・再現手段で答えます。
01
Completeness
SHIPPED, NOT MOCKED
A single run goes photo → explanation → live sandbox → typed form → human approval → submission → verifier exit 0 → receipt → teardown.
▸ npm test — verifier + guardrail unit tests
▸ 5 municipal procedures available in the target portal
▸ Failure paths: cancel, read failure, timeout, unreachable site
02
Innovation
AUDITABLE AGENCY
Most agents are judged on what they produce. Ours is judged on what it can prove: every value carries its origin, and the proof is checked by a program, not the model.
▸ Code-level refusal of unsourced values
▸ “Declared not-applicable” instead of silent omission
▸ The approver sees values grouped by origin
03
Real-life problem solving
NOT A DEMO-GRAM
The bottleneck is not understanding the letter — it is the 20 minutes of typing after it. That labour currently lands on an adult child, by phone, with the parent’s password.
▸ Two personas, one handoff, three human actions
▸ Works on real municipal portal layouts (not a toy form)
▸ Deadlines are the unit of value, not messages
04
Sponsored product usage
CORE LOOP
Daytona is the execution substrate: nine SDK surfaces, one sandbox per errand, deleted at the end. Nosana is the privacy-safe inference path for documents full of personal data.
▸ Remove Daytona and the product does not exist
▸ Remove Nosana and PII must go to a commercial API
▸ Provider switches keep both honest
