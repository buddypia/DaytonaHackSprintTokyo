## A. CrashTest — エージェントチームの衝突試験

チーム定義ファイル1枚を投入すると、数十の災害シナリオに並列でぶつけ、星評価と修正案を出します。

- **課題**: エージェントチームを本番に入れる前に、安全性を確かめる手段がない。
- **Daytona**: シナリオごとに使い捨てのマシンとおとり認証情報を用意し、並列に実行する。
- **Nosana**: 攻撃文を生成するレッドチームモデルを GPU 上の OSS モデルで動かす。
- **移植**: `shared/package-format.ts`、`evals/` のシナリオと採点器、`server/sentinel/`、`shared/redact.ts`。
- **弱点**: シナリオの質が勝負。事前に3〜5本を作り込む必要がある。

## B. FreezeFrame — 障害の瞬間を冷凍して並列修正

再現しにくいバグを一度だけ再現し、その状態を `fork()` で複製して、Bot ごとに別の仮説で修正を競わせます。

- **Daytona**: メモリ状態ごとの fork が核。VM サンドボックス限定で、所要時間は未計測。
- **移植**: Webhook トリガー、`coordinate_bots`、イベントバス。
- **弱点**: 「並列エージェントでバグ修正」は他チームと被りやすい。

## C. DayOne — 新人 Bot が README を実行して直す

まっさらなマシンで新人 Bot が手順書を上から実行し、詰まった箇所を修正して、ゼロから再検証できた手順書を PR にします。

- **課題**: README は腐る。新人のオンボーディングが止まる。
- **Daytona**: 誰の環境にも依存しない新品のマシンが検証の前提。
- **移植**: スケジュールトリガー、`coordinate_bots`、headless CLI の終了コード設計。
- **弱点**: 確実に動くが驚きは小さい。Nosana の必然性が薄い。

## D. Tournament — 動く試作4つから選ぶ

起動済みの開発サーバーごと4体に複製し、別モデルの Bot が同じ要望を別解釈で実装して、プレビュー URL を4面並べます。

- **弱点**: 並列生成ツールは既に多く、独自性は中程度。

## E. Downstream — リリース前に下流を全部テストする

ライブラリの変更を公開する前に、それに依存している下流リポジトリ N 個のテストを並列に走らせ、壊す相手を一覧にします。Rust コンパイラが持つ crater の仕組みを、どの言語のライブラリ作者にも提供する発想です。

- **課題**: 破壊的変更は公開後に利用者の CI が落ちて初めて分かる。メンテナは下流を試す手段を持たない。
- **デモ**: PR の URL を貼ると、下流 30 リポジトリがグリッドで点灯。3つが赤になり、原因の変更行と、下流それぞれへの修正パッチ案が出る。
- **Daytona**: 下流ごとに依存関係の異なる環境が要る。並列ファンアウトがそのまま効く。
- **Nosana**: 失敗ログの要約とパッチ生成を OSS モデルで回す程度。必然性は弱い。
- **移植**: Webhook トリガー（PR イベント）、Sentinel の失敗グルーピング（同一原因をまとめる）、headless CLI（CI から終了コードで使う）、イベントバス。
- **弱点**: 下流のテストが元から落ちている場合の切り分けが必要。変更前後の2回実行で対処する。

## F. MysteryShopper — ペルソナ Bot の覆面調査

高齢者、スクリーンリーダー利用者、英語話者、低速回線など、ペルソナごとの Bot が専用デスクトップで実際の申込・購入フローを試し、詰まった箇所を画面録画つきで報告します。

- **課題**: 離脱の原因は数字では分かるが、どこで何に詰まったかは人を集めて試さないと分からない。
- **デモ**: URL を貼ると6つのデスクトップでカーソルが同時に動く。「英語話者は住所入力で離脱」「キーボードだけでは決済ボタンに届かない」が証拠画面つきで出る。
- **Daytona**: `computerUse` の VNC デスクトップをペルソナごとに持つ。
- **Nosana**: 画面を見て操作する視覚モデルを GPU で動かす。必然性が強い。
- **移植**: Bot ごとの専用コンピュータ（`CloudBackend` に `"daytona"` を追加）、コンピュータパネルのライブ表示、チームパッケージ（ペルソナ集を1ファイルで配布）。
- **弱点**: 視覚モデルの操作精度に依存する。対象サイトを事前に決めて確認しておく必要がある。

## G. ReproCourt — 論文の主張を再実行して判定する

論文と付属リポジトリの URL を貼ると、Bot が環境を構築して実験を再実行し、論文の数値と実測を突き合わせて「再現 / 部分再現 / 再現不能」を判定します。

- **課題**: 公開コードがあっても動かない論文が多く、追試に数日かかる。
- **デモ**: 小さな論文1本で、表の数値3つのうち2つが一致、1つが乖離と表示する。
- **Daytona**: 論文ごとに依存関係の地獄を隔離して解く。
- **Nosana**: 実験そのものを GPU で走らせる。スポンサー2社の役割分担が最も明快。
- **移植**: `coordinate_bots`（環境構築 Bot → 実行 Bot → 判定 Bot）、ランタイムイベント、headless CLI の `--export`。
- **弱点**: 実験時間が長い。2分に収まる軽量な題材の事前選定が必須。

## H. TicketRepro — 問い合わせ文から不具合を再現する

「保存ボタンを押しても反映されない」といった問い合わせを受けると、Bot がサンドボックスでアプリを起動して実画面で再現し、再現動画と失敗する自動テストを添えて Issue を起こします。

- **課題**: サポートから開発への引き継ぎで「再現手順不明」のまま止まるチケットが多い。
- **デモ**: 問い合わせ Webhook が届く → Bot が画面を操作して現象を再現 → 赤いテストつきの Issue ができる。
- **Daytona**: アプリ本体とデスクトップを同じサンドボックスに置く。
- **Nosana**: 画面操作の視覚モデル。
- **移植**: Webhook トリガー、`coordinate_bots`（サポート Bot → QA Bot）、ブラウザ統合。
- **弱点**: B と課題領域が近い。再現できなかった場合の見せ方を決めておく必要がある。

## I. GoldenMaster — 旧システムの挙動を記録して移植を証明する

古いランタイムのシステムを当時のイメージで起動して入出力を記録し、新しいスタックへ移植したうえで、同じ入力に対する差分がゼロになるまで直します。

- **課題**: 仕様書のないレガシーシステムは、移植後に同じ動きをする保証が取れない。
- **デモ**: 左に旧環境、右に新環境。差分 47 件が 0 件まで減っていく。
- **Daytona**: 旧環境と新環境を並べて同じ入力を流す。古いランタイムの隔離に向く。
- **Nosana**: 移植コード生成を OSS モデルで行う程度。
- **移植**: evals の決定論的な再生と採点、イベントバス、Bot ごとの専用コンピュータ。
- **弱点**: 題材のレガシーアプリを事前に用意する必要がある。

## J. Quarantine — パッケージを入れる前に隔離環境で動かす

依存パッケージの追加や更新の PR が来ると、そのパッケージを使い捨てのマシンに入れて実際に動かし、インストール時と実行時の挙動を観察して報告します。

- **課題**: 悪意のあるパッケージは、インストールスクリプトで認証情報を盗む。コードを読むだけの検査では見逃す。
- **デモ**: PR の URL を貼ると、3つの依存のうち1つが「インストール中に ~/.ssh を読み、外部へ通信」と赤く表示され、通信先とファイルアクセスの記録が出る。
- **Daytona**: 危険かもしれないコードを自分の PC や CI で動かさずに済む。おとりの認証情報を置ける。
- **Nosana**: 難読化されたスクリプトの読解を OSS モデルで行う程度。必然性は弱い。
- **移植**: Webhook トリガー、イベントバス、`shared/redact.ts`、Sentinel の集約、headless CLI の終了コード。
- **弱点**: 既存の商用サービスがある領域。デモ用の「悪いパッケージ」は自作し、実在のマルウェアは使わない。A とおとりの仕組みが重なる。

## K. Bisect — 壊れたコミットを並列実行で一度に特定する

「先週は動いていた」という報告を受けると、その間の全コミットをそれぞれ別のマシンで同時にテストし、最初に壊れたコミットを特定して、修正 PR まで出します。

- **課題**: `git bisect` は1コミットずつ順番に試すので、ビルドが長いと数時間かかる。再現手順を書くのも人手。
- **デモ**: Issue の URL を貼ると、32 コミットが横一列に並び、左から緑、途中から赤に変わる。境目のコミットが強調され、その差分と修正案が出る。
- **Daytona**: コミットごとに依存関係が違う。並列に作れることがそのまま速さになる。
- **Nosana**: Issue 文から再現テストを書く部分を OSS モデルで行う程度。
- **移植**: Webhook トリガー（Issue イベント）、`coordinate_bots`（再現 Bot → 探索 Bot → 修正 Bot）、イベントバス、headless CLI。
- **弱点**: 仕組みが単純で、驚きは「速さ」に限られる。B・H と領域が近い。

## L. FireDrill — 障害対応の手順書を実際に試す

障害対応の手順書（runbook）を渡すと、本番を模した複製環境にわざと障害を起こし、当番 Bot が手順書だけを頼りに復旧を試みます。復旧できなかった手順を直し、もう一度壊して確かめます。

- **課題**: 手順書は障害の最中に初めて実行され、そのとき初めて古いと分かる。訓練は手間がかかるので行われない。
- **デモ**: 手順書を入れる → DB 接続を切る → 当番 Bot が手順3で「そのコマンドは存在しない」と止まる → 手順書を修正 → 再度壊して 40 秒で復旧。
- **Daytona**: 壊してよい複製環境が要る。壊す前の状態をスナップショットにして、何度でもやり直す。
- **Nosana**: 必然性は弱い。
- **移植**: スケジュールトリガー（毎週の訓練）、`coordinate_bots`（障害役 Bot → 当番 Bot → 修正 Bot）、evals の採点器（復旧までの秒数）、Sentinel。
- **弱点**: C と骨格が同じ（手順書を実行して直す）。複製環境を小さく作り込む準備が要る。

## M. TuneOff — 小型モデルの微調整を並列に競わせる

データセットと「何を当てたいか」を渡すと、複数の小型モデルと設定で微調整を並列に走らせ、同じ評価で比べて最良の1つを返します。

- **課題**: 自社データで小型モデルを作りたいが、どのモデルとどの設定がよいかは試さないと分からない。試すたびに環境構築がいる。
- **デモ**: 問い合わせ分類のデータ 500 件を入れる → 6つの組み合わせが並んで学習 → 正解率の棒が伸び、1位のモデルがその場で呼び出せる。
- **Daytona**: 評価ハーネスとデータ前処理を隔離して実行し、評価条件をそろえる。
- **Nosana**: 学習そのものを GPU で走らせる。全案の中で Nosana の比重が最も大きい。
- **移植**: evals の決定論的な採点、イベントバス、headless CLI の `--export`、チームパッケージ（実験計画を1ファイルで配布）。
- **弱点**: 学習が2分に収まらない。ごく小さいモデルとデータに絞るか、途中経過を録画で見せる必要がある。Daytona が脇役になる。

## N. TakeHome — 採用課題の提出物を隔離実行して採点する

候補者が提出したコーディング課題のリポジトリを使い捨てのマシンで実行し、隠しテストの結果、起動した画面、設計上の気になる点をまとめ、面接で聞く質問を作ります。

- **課題**: 提出物の確認は現場のエンジニアが1件 30 分以上かけている。見知らぬ人のコードを自分の PC で動かすのも避けたい。
- **デモ**: 提出物3件の URL を貼ると、3台で同時にビルドとテストが走り、合格数とプレビュー URL、候補者ごとの質問3つが並ぶ。
- **Daytona**: 見知らぬコードの隔離実行と、起動した画面のプレビュー URL。
- **Nosana**: コードの読解と質問生成を OSS モデルで行う。候補者のコードを外部 API に送らない理由になる。
- **移植**: Webhook トリガー（提出イベント）、`coordinate_bots`（実行 Bot → 講評 Bot）、headless CLI、`shared/redact.ts`（個人情報の伏せ字）。
- **弱点**: 合否の判断を AI に寄せると反発を招く。判断材料の提示に留める。技術的な新しさは小さい。

## O. LinkCheck — 怪しいリンクを隔離マシンで代わりに開く

高齢者に届いた SMS やメールを転送すると、Bot が使い捨てのマシンでリンクを実際に開き、おとりの個人情報を入力して何が起きるかを観察します。結果は「詐欺です。開かないでください」のように大きな字と音声で返し、家族にも同じ内容を通知します。

- **課題**: 宅配の不在通知や銀行を装うフィッシングは、文面だけでは見分けにくい。高齢者は「開いて確かめる」ことができない。
- **デモ**: 自作の偽「不在通知」SMS を転送する。ライブ画面で Bot が偽サイトを開き、カード番号欄におとりの番号を入れる。送信先が宅配会社と無関係なドメインだと分かり、赤い判定と音声が返る。本物の通知でも試し、緑になることを見せる。
- **Daytona**: 危険なリンクを開く場所として隔離が必須。デスクトップの画面をそのまま見せられる。
- **Nosana**: 画面を読む視覚モデルと音声合成。届いた文面には個人情報が含まれるため、外部 API に送らない理由になる。
- **移植**: Webhook トリガー（転送の受信）、`runtime-events` → SSE（ライブ画面）、`shared/redact.ts`（個人情報の伏せ字）、headless CLI。
- **弱点**: 判定を誤ると被害に直結するため、「安全」とは断定せず「確認できた事実」を返す設計にする。デモ用の偽サイトは自作する。J とおとりの仕組みが重なる。

## P. SilverPass — 高齢者がその手続きを最後まで終えられるかを試す

F（MysteryShopper）のペルソナを高齢者だけに絞った版です。老眼（拡大 200%）、手の震え（クリック位置がずれる）、カタカナ用語が分からない、入力が遅くてタイムアウトする、といった条件の Bot が、行政・銀行・病院のオンライン手続きを最初から最後まで試します。

- **課題**: 手続きのオンライン化が進むほど、高齢者が窓口に戻ってくる。提供側は、高齢者がどこで諦めたかを知る手段がない。
- **デモ**: 自作の「給付金申請フォーム」の URL を貼ると、4人の高齢者ペルソナが同時に操作を始める。完了は 1/4。原因は「15 分で無言のタイムアウト」「ボタンが小さく誤タップ」「『マイナポータル連携』の意味が分からず停止」。
- **Daytona / Nosana**: F と同じ（デスクトップつきサンドボックスと視覚モデル）。
- **移植**: F と同じ。ペルソナを Markdown 1枚で配布する `package-format` がそのまま使える。
- **弱点**: F と同じ（視覚モデルの操作精度、デスクトップ複数台の同時起動）。利用者は高齢者本人ではなく、自治体や事業者になる。

## Q. Yubin — 紙の通知を読んで手続きまで済ませる

役所や年金機構から届いた紙の通知を撮影すると、「何の通知か、いつまでに何をするか」を平易な言葉で説明し、同封の申請書を記入した PDF まで作ります。

- **課題**: 通知の文面が難しく、放置して期限を過ぎる高齢者が多い。家族が電話で読み上げてもらって対応している。
- **デモ**: 通知の写真を1枚送る。「介護保険の負担割合の更新です。7月31日までに返送が必要です」と表示され、記入済みの申請書 PDF と、家族向けの要約が出る。
- **Daytona**: PDF の記入と検証（記入漏れの検査）を隔離環境で実行する。
- **Nosana**: 文書の読み取りを OSS の視覚モデルで行う。個人情報を外部 API に送らない理由になる。
- **移植**: Webhook トリガー、`coordinate_bots`（読解 Bot → 記入 Bot → 検査 Bot）、`shared/redact.ts`。
- **弱点**: Daytona の必然性が弱く、文書読み取りの API ラッパーに見えやすい。

## R. Otsukai — 声で頼むと Bot が代わりに画面を操作する

高齢者が「来週の火曜に整形外科を予約して」と声で頼むと、Bot が隔離デスクトップで予約サイトを操作し、確定の直前で止まって内容を読み上げます。

- **課題**: 通院予約やネットスーパーはオンライン前提になったが、高齢者は画面操作でつまずき、家族が代行している。
- **デモ**: 音声で依頼すると、ライブ画面で Bot が自作の予約サイトを操作し、「火曜 10 時で予約します。よろしいですか」と読み上げる。
- **Daytona**: 利用者ごとの専用デスクトップ。ログイン状態を残したまま休止・再開できる。
- **Nosana**: 音声認識、視覚モデル、音声合成。
- **移植**: Bot ごとの専用コンピュータ（`CloudBackend` に `"daytona"` を追加）、`runtime-events` → SSE。
- **弱点**: 確定前の確認が主役になると、却下した Kagemusha に近づく。本物のサイトの自動操作は利用規約に触れるため、デモは自作サイトに限る。会場での音声入力は失敗しやすい。
