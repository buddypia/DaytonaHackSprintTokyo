# Q+R. おまかせ手続き（Omakase Tetsuzuki）— 届いた通知を撮るだけで、AI がパソコン操作を代わりにして手続きを済ませる

[Q. Yubin](./idea-q-flow.html)（紙の通知を読んで申請書を記入する）と [R. Otsukai](./idea-r-flow.html)（声で頼むと Bot が画面を操作する）を1本にまとめた案です。

- 状態: 候補段階。未実装・未検証。数値はすべて説明用の想定値です。
- 作成: 2026-11-13
- 実装用の文書: [`BRIEF.md`](../BRIEF.md) / [`PRD.md`](../PRD.md) / [`SPEC.md`](../SPEC.md)

## 一言でいうと

役所から届いた紙の通知を撮影すると、「何の通知で、いつまでに何をするか」を3行で説明します。オンラインで済む手続きなら、Bot が利用者専用の隔離マシンで電子申請サイトを開き、通知の内容を転記して送信の直前まで進めます。分からない項目は声で質問し、最後に送信内容を読み上げて「はい」の返事で送信します。送信後は、送った内容と通知の内容をプログラムで突き合わせ、一致を確かめてから家族に知らせます。

## なぜ統合するのか

2案はそれぞれ単独では弱点がありましたが、組み合わせると互いの弱点を埋めます。

| | Q. Yubin 単独 | R. Otsukai 単独 | 統合後 |
|---|---|---|---|
| 起点 | 紙の通知（自然） | 声の依頼（会場で失敗しやすい） | 紙の通知。声は質問への返事だけに使う |
| 出口 | 記入済み PDF（本人が投函） | 予約の確定 | 電子申請の送信と、送信内容の検証まで |
| Daytona の必然性 | 弱い（PDF 記入だけ） | 強い（専用デスクトップ） | 強い。隔離マシンでサイトを操作し、検証スクリプトも同じマシンで動かす |
| 文書読み取りの API ラッパーに見えるか | 見える | 見えない | 見えない。読んだ後に実際の手続きを完了させる |
| 承認ゲート型（却下済み Kagemusha）との距離 | 遠い | 近い（確定前の確認が目立つ） | 遠い。主役は「紙1枚から手続き完了まで」で、確認は1工程にすぎない |
| 何を頼めばよいか | 通知が教えてくれる | 本人が言葉にする必要がある | 通知が教えてくれる。本人は頼み方を考えなくてよい |

## 利用場面

一人暮らしの 78 歳の母親と、離れて暮らす娘を例にします。

- **困っていること**: 介護保険や給付金の通知が届くたびに、何をすればよいか分からない。最近は「電子申請でもできます」と書いてあるが、画面の操作ができない。分からないまま置いておき、期限を過ぎる。
- **今のやり方**: 娘に電話して文面を読み上げる。娘は仕事の合間に内容を調べ、母親の ID とパスワードを預かって代わりに申請する。1通に 30〜60 分かかる（想定値）。
- **おまかせ手続きだと**: 通知を撮影して送る。3行の説明が大きな字と音声で届き、Bot が申請を進める。母親は2つの質問に声で答え、読み上げられた内容に「はい」と言うだけ。娘には完了の通知と、送った内容の控えが届く。

## 処理の流れ

| # | 工程 | 担当 | 内容 |
|---|---|---|---|
| 1 | 受け取る | Web アプリ | 通知の写真を受け取る。記録には個人情報を伏せ字にして残す |
| 2 | 読む | Nosana（視覚モデル） | 通知の種類、期限、やること、転記できる値（氏名・住所・被保険者番号など）を構造化して取り出す |
| 3 | 説明する | Web アプリ | 3行の説明を大きな字で表示し、ブラウザの音声合成で読み上げる |
| 4 | 専用マシンを起こす | Daytona | 利用者ごとのサンドボックスを作成（または休止から再開）。中で電子申請サイト（デモは自作）とブラウザ自動操作を動かす |
| 5 | 申請を進める | Daytona + LLM | ページの入力欄を読み取り、通知の値を対応づけて入力する。画面はライブで家族も見られる |
| 6 | 質問する | Web アプリ | 通知から分からない項目（収入の変化、振込口座など）を声で質問し、返事を入力に使う |
| 7 | 読み上げて送信 | Web アプリ + Daytona | 送信内容を読み上げ、「はい」で送信、「いいえ」で何も送らずに終了 |
| 8 | 検証する | Daytona | 送信された内容と通知から読んだ値を検証スクリプトで突き合わせる。`exitCode === 0` で合格 |
| 9 | 知らせる | Web アプリ | 受付番号と控えを本人と家族に届け、サンドボックスを休止または破棄する |

## 2分デモの台本

| 時間 | 内容 |
|---|---|
| 0:00–0:15 | 課題を言う。実物に似せた通知書を見せ、「これが届いて、何をすればよいか分かりますか」 |
| 0:15–0:30 | 通知書を撮影して送る（撮影に失敗したときのために、同じ画像を送るボタンを用意する） |
| 0:30–0:45 | 「介護保険の負担割合の更新です。7月31日までに申請が必要です。電子申請でできます」が大きな字と音声で出る |
| 0:45–1:20 | Daytona のサンドボックスが起動し、ライブ画面で Bot が電子申請サイトに通知の値を入力していく。質問2つに声（または予備のボタン）で答える |
| 1:20–1:40 | 「この内容で申請します。よろしいですか」の読み上げに「はい」。送信後、検証スクリプトが走り、`exit 0` と受付番号が出る |
| 1:40–2:00 | 家族に届いた通知を見せて締める。「読めなかった通知が、『はい』と言うだけで終わる」 |

## スポンサー製品の役割

- **Daytona**: 利用者ごとの隔離マシン。電子申請サイトの操作、送信内容の検証スクリプトの実行、ライブ画面の配信をすべてこの中で行う。ログイン状態を残したまま休止・再開でき、家族の PC に ID とパスワードを置かずに済む。他人の個人情報と混ざらず、不要になれば環境ごと破棄できる。
- **Nosana**: 通知の文面を読む OSS の視覚モデルと、入力欄への対応づけを行う LLM を GPU 上で動かす。通知には氏名・住所・被保険者番号が載るため、外部の API に送らず自分で動かすモデルを使う理由になる。

## 弱点と対策

- **読み間違い**: 期限や番号を誤ると本人が不利益を受ける。説明には原文の該当箇所を並べ、送信後の検証で通知の値と照合する。
- **本物の電子申請サイトは使えない**: 自動操作は利用規約に触れることが多い。デモは自作の「電子申請サイト」に限る。実用には自治体や事業者との連携が要る。
- **会場での音声入力**: 騒音で失敗しやすい。質問への返事はボタンでも答えられるようにする。
- **75分で作れるか**: 画面を見て操作する視覚モデルは使わず、ページの入力欄を DOM から読み取って入力する方式にする。視覚モデルは通知の読み取りだけに使う。
- **代行の範囲**: 署名や本人確認（マイナンバーカード）が要る手続きは対象外とし、「窓口に持っていくもの」の案内に留める。
